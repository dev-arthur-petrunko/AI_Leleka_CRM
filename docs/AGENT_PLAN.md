# AI Leleka CRM — план работ для агента-разработчика

> Положите этот файл в репозиторий как `docs/AGENT_PLAN.md`. Агент (Claude Code или другой) выполняет его **по фазам**, одна фаза = одна ветка = один pull request (запрос на слияние кода, по которому вы смотрите изменения перед принятием).
> Цель: превратить CRM «для лидов» в CRM, к которой можно подключать интернет-магазины (Prom, Rozetka, сайты), не рискуя данными клиентов.

---

## 0. Словарь (простыми словами)

| Термин | Что это | Аналогия |
|---|---|---|
| Tenant (тенант) | Одна компания-клиент вашего SaaS со своими данными | Отдельная квартира в многоквартирном доме |
| Идемпотентность | Повторное выполнение одной операции даёт тот же результат, что одно | Кнопка лифта: сколько ни жми, лифт приедет один |
| Вебхук (webhook) | Внешний сервис сам «стучит» в ваш API, когда что-то случилось | Курьер звонит в домофон |
| Polling (опрос) | Ваш сервер сам периодически спрашивает: «есть новые заказы?» | Вы сами ходите проверять почтовый ящик |
| Воркер (worker) | Фоновый процесс, который делает работу вне запроса пользователя | Повар на кухне, пока официант принимает заказы |
| HMAC-подпись | Хеш от тела письма с общим секретом; доказывает, что отправитель знает секрет | Печать на конверте |
| Миграция (Alembic) | Скрипт, который меняет структуру БД по версиям | Инструкция по перестройке здания по этапам |
| CI | Автоматический запуск тестов при каждом коммите | Контролёр на входе, который проверяет каждого |
| N+1 запрос | На каждую строку результата делается отдельный запрос в БД | Ходить в магазин за каждым продуктом отдельно |
| RFM | Сегментация клиентов: давность, частота, сумма покупок | Оценка постоянного посетителя кафе |
| LTV / AOV | Сколько клиент принёс за всё время / средний чек | Общая выручка с гостя / средний счёт |
| SKU | Внутренний артикул товара | Штрихкод в вашей системе |
| ТТН | Товарно-транспортная накладная Новой Почты (номер посылки) | Номер для отслеживания |

## 1. Как запускать агента и какие навыки (skills) подключить

### 1.1 Что такое skill
Skill (навык) — папка с файлом `SKILL.md`: инструкции, которые агент подгружает только когда задача подходит под описание. Аналогия: справочник в ящике стола, который достают по теме, а не читают целиком каждый раз. Для Claude Code навыки проекта лежат в `.claude/skills/<имя-навыка>/SKILL.md` (в репозитории, версионируются вместе с кодом) или глобально в `~/.claude/skills/`. Важно: путь строго `.claude/skills/<имя>/SKILL.md`; файл без подпапки игнорируется.

### 1.2 Где взять готовые навыки

| Источник | Что даёт | Как поставить |
|---|---|---|
| Официальный репозиторий Anthropic: `github.com/anthropics/skills` | Примеры и документ-навыки (docx, pdf, pptx, xlsx), шаблон нового навыка в `./template`, спецификация в `./spec` | В Claude Code: `/plugin marketplace add anthropics/skills`, затем `/plugin install document-skills@anthropic-agent-skills` или `/plugin install example-skills@anthropic-agent-skills` |
| Спецификация формата | Как правильно писать `SKILL.md` | `agentskills.io` |
| Сообщество (например, `obra/superpowers`: навыки про TDD, план, code review; есть и другие коллекции) | Готовые процессы разработки | Ставить через `/plugin marketplace add <владелец/репозиторий>`. **Перед установкой прочитайте `SKILL.md` и скрипты**: навык может запускать код на вашей машине |
| Каталог `skills.sh` | Поиск навыков разных авторов | Так же, проверять содержимое перед использованием |

Совет: для этого проекта вам не нужен десяток чужих навыков. Достаточно **4 своих** (тексты ниже, раздел 1.4) и 1–2 готовых про процесс (тесты и code review).

### 1.3 MCP-серверы (подключаемые инструменты агента)
MCP (Model Context Protocol) — стандарт, по которому агенту дают «руки»: доступ к БД, браузеру, GitHub. Добавляются командой `claude mcp add ...` (точные параметры смотрите в README каждого сервера).

| Инструмент | Зачем в этом проекте |
|---|---|
| GitHub MCP (официальный сервер GitHub) | Создавать ветки, PR, читать CI-результаты |
| Postgres MCP (любой поддерживаемый сервер) | Смотреть схему и проверять SQL на **тестовой** базе; подключать только к dev-БД, никогда к боевой |
| Playwright MCP (от Microsoft) | Агент открывает `frontend-preview` в браузере, кликает и делает скриншоты, чтобы проверить, что UI не сломан |

### 1.4 Четыре собственных навыка проекта (создать в фазе 0)

**`.claude/skills/leleka-tenant-isolation/SKILL.md`**
```markdown
---
name: leleka-tenant-isolation
description: Use whenever adding or changing any API endpoint, query, worker or webhook handler in AI Leleka CRM that touches business tables (clients, deals, orders, tasks, integrations, webhook_events). Enforces multi-tenant isolation.
---
# Правила изоляции тенантов
1. Каждый запрос к бизнес-таблице содержит `Model.tenant_id == tenant_id`; tenant_id берётся ТОЛЬКО из JWT (`get_current_tenant`) или из проверенной интеграции. Никогда из body/query.
2. Каждый эндпоинт имеет явную зависимость: `get_current_user` / `require_role(...)`. Публичные эндпоинты перечислены в tests/test_public_endpoints.py.
3. Уникальные ключи всегда включают tenant_id: UNIQUE(tenant_id, ...).
4. Воркеры получают tenant_id явно и фильтруют по нему.
5. Для каждого нового эндпоинта добавь тест: пользователь тенанта B получает 404/403 на объект тенанта A.
6. Перед завершением: `pytest backend/tests -k tenant`.
```

**`.claude/skills/leleka-integration-adapter/SKILL.md`**
```markdown
---
name: leleka-integration-adapter
description: Use when adding or modifying an external integration (marketplace, shop platform, delivery, payment, messenger) in AI Leleka CRM.
---
# Как добавлять интеграцию

6. Тесты работают на записанных ответах провайдера (fixtures в tests/fixtures/<provider>/), без реальной сети.
7. Формат API провайдера сверяй с его официальной документацией, не по памяти.
```

## Фаза 1. Безопасность (3–5 дней)

### 1.1 Закрыть `/webhooks/pending`
**Проблема:** `backend/app/api/webhooks.py`, `GET /webhooks/pending` без авторизации отдаёт события всех тенантов (имена, телефоны, суммы).
**Что:** удалить публичный эндпоинт. Если нужен для отладки, то `Depends(require_role("owner","admin"))` и фильтр `tenant_id == user.tenant_id`. Воркер читает БД напрямую, HTTP ему не нужен.
**Готово, когда:** тест 0.3 зелёный, без токена возвращается 401.

### 1.2 Подпись и секрет вебхуков
**Проблема:** тенант определяется по `?tenant=slug` (его легко угадать), подписи нет: любой может вбросить фальшивые заказы.
**Что:**
1. В таблицу `integrations` добавить `webhook_secret` (случайная строка 32+ байта, генерируется при создании интеграции, хранится шифрованно или хешем).
2. Новый маршрут `POST /webhooks/{provider}/{integration_id}`. Тенант определяется по `integration_id`, а не по slug.
3. Проверка: если провайдер подписывает тело, проверять HMAC; если нет (часть маркетплейсов не подписывает), секрет передаётся в заголовке или последним сегментом URL и сравнивается через `hmac.compare_digest`.
4. Неизвестный `integration_id` или неверная подпись → 404/401 без подробностей.
5. Ограничение размера тела (например 1 МБ) и rate-limit на маршрут.

```python
import hmac, hashlib

def verify_signature(secret: str, body: bytes, signature: str | None) -> bool:
    expected = hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature or "")
```
**Готово, когда:** запрос без подписи отклонён; запрос с подписью другого тенанта отклонён; в UI интеграции показан готовый URL вебхука для копирования.

### 1.3 Дедупликация вебхуков с учётом тенанта
**Проблема:** уникальность `(provider, external_id)` без `tenant_id`: заказ №1001 одного магазина блокирует №1001 другого.
**Что:** миграция: удалить старый unique, создать `UNIQUE(tenant_id, provider, external_id)`; `tenant_id` в `webhook_events` сделать NOT NULL (события без тенанта не принимаем). Если `external_id` пустой, считать хеш тела (`sha256(body)`) как `external_id`.

### 1.4 Вход с учётом компании
**Проблема:** `auth.py::login` ищет `User.email == form.username` без тенанта; уникальность в схеме `(tenant_id, email)`.
**Что:** использовать поле `client_id` стандартной OAuth2-формы как slug компании: `User` ищется по `(tenant.slug, email)`. В `login.html` добавить поле «Компанія» (запоминать в localStorage). Альтернатива: сделать email глобально уникальным (проще, но один человек не сможет работать в двух компаниях).
**Готово, когда:** тест «два тенанта с одинаковым email логинятся каждый в свой».

### 1.5 Аккаунты: пароль, токены
- `users.must_change_password` (bool): приглашённый с временным паролем обязан сменить его при первом входе (`POST /auth/change-password`).
- Сброс пароля по email (одноразовая ссылка, живёт 30 минут, хранить только хеш токена) — нужен почтовый транспорт: `backend/app/integrations/email.py` уже есть.
- Подтверждение email при регистрации.
- Отзыв токенов: `users.token_version`; в JWT кладётся версия; при смене пароля версия растёт, старые токены перестают работать. Время жизни access-токена снизить с 24 часов до 30–60 минут + refresh-токен.
- 2FA (TOTP, коды из приложения-аутентификатора) для ролей `owner`/`admin`: библиотека `pyotp`.
- Политика пароля: минимум 10 символов, проверка по списку частых паролей.
- Rate-limit не только на `/auth/login`, но и на `/auth/register`, сброс пароля, `/auth/invite`.

### 1.6 Инфраструктура
**Что:** отдельный `docker-compose.prod.yml`:
- без публикации портов Postgres и Redis наружу (`ports:` убрать, сервисы доступны только внутри сети Docker);
- пароли БД и Redis из `.env`, `redis --requirepass`;
- убрать `--reload`, запуск через `gunicorn -k uvicorn.workers.UvicornWorker` или `uvicorn --workers 2`;
- обратный прокси (Caddy или nginx) с HTTPS (Let's Encrypt);
- `healthcheck` для api;
- ежедневный бэкап Postgres (`pg_dump` в отдельное хранилище) и проверка восстановления.
В `docker-compose.yml` (dev) оставить как есть.

### 1.7 Гигиена секретов
- Старый `SECRET_KEY` остался в истории git: на проде использовать только новый (runbook в README уже есть).
- Добавить `gitleaks` (или `git-secrets`) в CI, чтобы ключи не попадали в коммиты.
- Проверить `backend/.env.example`: только пустые значения.

### 1.8 Молчаливые моки на фронте
**Проблема:** `frontend-preview/assets/api.js`: при любой ошибке возвращает `null`, и экран показывает выдуманные демо-данные. Менеджер не узнает, что сервер недоступен.
**Что:** `api()` возвращает `{ok, data, error}`. Каждый экран показывает баннер «Немає звʼязку з сервером. Показано не ваші дані» при ошибке, и отдельный явный демо-режим (`?demo=1`) с постоянной плашкой «Демо». 401 → редирект на логин, 402 → предложение тарифа.

### 2.2 Нормализация телефонов и поиск клиента
**Проблема:** `import_orders` ищет клиента по строке телефона; `+380…`, `380…`, `0…` дают разных людей.
**Что:** `backend/app/core/phones.py`, вызывать при сохранении клиента и при импорте; в `clients` хранить нормализованный `phone` и индекс `(tenant_id, phone)`; миграция-скрипт, который нормализует существующие записи и помечает дубли.

```python
import re

def normalize_phone(raw: str | None, default_cc: str = "380") -> str | None:
    if not raw:
        return None
    d = re.sub(r"\D", "", raw)
    if d.startswith("00"):
        d = d[2:]
    if len(d) == 10 and d.startswith("0"):   # 0501234567
        d = default_cc + d[1:]
    elif len(d) == 9:                        # 501234567
        d = default_cc + d
    if not 11 <= len(d) <= 15:
        return None
    return "+" + d
```
Тесты: `0501234567`, `380501234567`, `+38 (050) 123-45-67`, `050 123 45 67` дают один результат `+380501234567`; мусор возвращает `None`.

### 2.3 Идемпотентный сервис импорта заказа
**Что:** `backend/app/services/orders.py::upsert_order(db, tenant_id, dto)`: единая точка входа для вебхуков, polling и ручного создания.

## Фаза 3. Синхронизация с магазинами (1–2 недели)

**Главная мысль:** основной путь получения заказов это **опрос API по курсору**, а вебхуки это ускоритель. Причина: у многих провайдеров вебхуков на заказы нет или они ненадёжны, а сторонние CRM-интеграции для Prom, например, обновляют заказы по расписанию раз в несколько минут. ### 3.1 Очередь задач и воркер
**Что:** Celery (или RQ / arq) на существующем Redis; сервисы `worker` и `beat` (планировщик) в `docker-compose`. Убрать ручные cron-скрипты (`stuck_checker.py`, `billing_recalc.py`, `feed_scheduler.py`), перевести их в периодические задачи.

### 3.2 Обработчик `webhook_events`
**Что:** задача каждые 10–30 секунд берёт пачку событий `SELECT ... FOR UPDATE SKIP LOCKED` (несколько воркеров не схватят одну запись), вызывает `upsert_order`, ставит `processed`; при ошибке `retry_count += 1`, `next_retry_at = now + min(2^retry_count минут, 60 минут)`; после N попыток статус `dead` и видимое уведомление владельцу.

### 3.3 Polling с курсором
**Что:** таблица `sync_state` (tenant_id, integration_id, cursor, last_success_at, last_error, consecutive_failures).
Задача `sync_integration(integration_id)` каждые 5–15 минут: читать заказы «с момента курсора» постранично, вызывать `upsert_order`, двигать курсор только после успешной записи страницы. Повторный запуск безопасен благодаря идемпотентности (2.3).
Учитывать лимиты провайдера: при HTTP 429 ждать `Retry-After`, иначе экспоненциальная пауза.

## Фаза 6. Аналитика магазина (1–2 недели)

### 6.1 Сначала починить производительность
**Проблема:** `backend/app/services/ai.py`: `churn_candidates()` загружает все сделки в память и делает запрос `Client` на каждого клиента (N+1); `next_best_actions()` тоже тянет таблицы целиком.
**Что:** перенести в SQL-агрегаты:
```sql
-- клиенты без активности 30+ дней (один запрос вместо N+1)
SELECT c.id, c.name, MAX(d.last_activity_at) AS last_act
FROM clients c
JOIN deals d ON d.client_id = c.id AND d.tenant_id = c.tenant_id
WHERE c.tenant_id = :tenant AND c.segment <> 'lost' AND c.deleted_at IS NULL
GROUP BY c.id, c.name
HAVING MAX(d.last_activity_at) < now() - interval '30 days'
ORDER BY last_act
LIMIT 20;
```
Добавить индексы `(tenant_id, last_activity_at)`, `(tenant_id, stage)`. Тест на 10 000 сделок: дашборд отвечает быстрее 500 мс.

### 6.2 Новые метрики (эндпоинты `/analytics/shop/...`)

| Метрика | Расчёт |
|---|---|
| Выручка и число заказов по дням/каналам | `SUM(total)`, `COUNT(*)` с `GROUP BY source, date_trunc('day', placed_at)` по оплаченным/доставленным |
| AOV (средний чек) | выручка / число заказов |
| LTV клиента | сумма всех оплаченных заказов клиента |
| Повторные покупки | доля клиентов с 2+ заказами за период |
| RFM-сегменты | давность последнего заказа, число заказов, сумма; квинтили через `NTILE(5)`; автоназначение сегмента вместо ручного `new/regular/vip/lost` |
| Когорты | группа по месяцу первой покупки × удержание по месяцам |
| Возвраты и отказы от посылок | доля `returned`, причины, потеря выручки |
| Время обработки | от `placed_at` до `shipped`, до `delivered` |
| ABC-анализ товаров | сортировка по выручке, накопленная доля: A до 80 %, B до 95 %, C остальное |
| Менеджеры | заказы, конверсия, время первого ответа, просроченные задачи |
| Маржа | нужна закупочная цена в каталоге (`catalog_products.cost`) |
| CAC / ROMI | после подключения рекламных кабинетов (Meta Ads, Google Ads) — позже |

Пример RFM-заготовки:
```sql
WITH base AS (
  SELECT client_id,
         now()::date - MAX(placed_at)::date AS recency_days,
         COUNT(*) AS frequency,
         SUM(total) AS monetary
  FROM orders
  WHERE tenant_id = :tenant AND status IN ('delivered') 
  GROUP BY client_id
)
SELECT client_id,
       NTILE(5) OVER (ORDER BY recency_days DESC) AS r,
       NTILE(5) OVER (ORDER BY frequency) AS f,
       NTILE(5) OVER (ORDER BY monetary) AS m
FROM base;
```
*(Замечание: в исходном тексте плана этот SQL-блок обрезан — агент должен дописать его по таблице 6.2.)*
